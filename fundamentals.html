Harness Engineering

Harness Engineering Fundamentals

Six core lectures extracted from the Learn Harness Engineering course. These principles form the foundation for every design pattern and case study that follows.

01

Why Capable Agents Still Fail

As of late 2025, the strongest coding agents on SWE-bench Verified achieve roughly 50–60%. And that's on carefully selected tasks with clear issue descriptions and existing test cases. Move to daily development — vague requirements, no existing tests, implicit business rules scattered everywhere — and that number only goes down.

Anthropic ran a controlled experiment. Same prompt ("build a 2D retro game maker"), same model (Opus 4.5). First run: bare, no support — 20 minutes, $9, the game's core features didn't work at all. Second run: full harness (planner + generator + evaluator three-agent architecture) — 6 hours, $200, the game was playable. They didn't change the model. What changed was the saddle.

Where agents actually get stuck:

  • Underspecified tasks. You say "add a search feature," and the agent's understanding is completely different from yours — search what? Full-text or structured? Pagination? Highlighting?
  • Implicit conventions. Your team standardized on SQLAlchemy 2.0 syntax, but the agent writes 1.x code by default. Rules that only exist in your head and a Slack message from three months ago.
  • Environment traps. Incomplete dev environment, missing dependencies, wrong tool versions. The agent burns precious context window on pip install failures instead of solving the actual task.
  • No verification. No tests, no lint, or verification commands never communicated. The agent writes code, looks at it, decides it's fine, says "done."
  • Context anxiety. When agents sense context is running low, they rush to finish, skip verification, and choose a simple solution over the optimal one.

Key terminology:

  • Capability Gap: The gulf between benchmark performance and real-task performance.
  • Harness: Everything outside the model — instructions, tools, environment, state management, verification feedback.
  • Harness-Induced Failure: The model has enough capability, but the execution environment has structural defects.
  • Verification Gap: The agent says "I'm done" when it's not done — the most common failure mode.
  • Diagnostic Loop: Execute, observe failure, attribute to a specific harness layer, fix that layer, re-execute.

Core principle: When things fail, don't swap the model first — check the harness. If the same model succeeds on similar, well-structured tasks, assume it's a harness problem. It's like a car breaking down — you don't immediately suspect the engine. You check if it's out of gas first.

02

What a Harness Actually Is

Most people mean "a prompt file" when they say harness. That's not a harness. It's like opening a restaurant with nothing but ingredients — no stove, no knives, no recipes, no plating workflow. That's not a restaurant. That's a refrigerator.

A harness consists of five subsystems, each with clear responsibilities and evaluation criteria:

📚

1. Instructions (Recipe Shelf)

AGENTS.md, CLAUDE.md, docs/ hierarchy. Project overview, tech stack versions, first-run commands, non-negotiable hard constraints, and links to detailed documentation.

🔧

2. Tools (Knife Rack)

Shell, file edit, search, test execution. Ensure the agent has sufficient tool access. Don't disable shell for "security" — if the agent can't run pip install, how is it supposed to work? But follow least-privilege principles.

💡

3. Environment (Stove)

Make the environment state self-describing. Use pyproject.toml or package.json to lock dependencies, .nvmrc or .python-version for runtime versions, Docker or devcontainers for reproducibility.

📋

4. State (Prep Station)

Long tasks need progress tracking. Use a simple PROGRESS.md file recording what's done, what's in progress, what's blocked. Update before each session ends, read when the next session starts.

✅

5. Feedback (Quality Check Window)

This is the highest-ROI subsystem. Explicitly list verification commands in AGENTS.md: tests, type checks, lint, full verification. Missing this is like cooking without ever tasting the food.

Use "isometric model control" to quantify each subsystem's marginal contribution: keep the model fixed, remove subsystems one at a time, measure which removal causes the biggest performance drop. That's your bottleneck — focus your effort there.

A team's real story: A team used GPT-4o on a TypeScript + React app (~20,000 LOC). Stage 1 (empty kitchen): 20% success. Stage 2 (recipe shelf): 60%. Stage 3 (quality check window): 80%. Stage 4 (prep station): 80–100%. Four iterations, same model, success rate went from 20% to near 100%. That's the power of harness engineering.

03

Repository as System of Record

Your team's architecture decisions are scattered across Confluence, Slack, Jira, and a few senior engineers' heads. For humans this barely works — you can ask a colleague, search chat history, dig through docs. But for an AI agent, information that's not in the repository simply does not exist.

An agent's inputs are: system prompts and task descriptions, file contents from the repository, and tool execution output. That's it. Your Slack history, Jira tickets, Confluence pages, and that architecture decision you discussed over coffee on Friday afternoon — the agent can't see any of it. It's an engineer locked inside the repository.

How to test whether your map is good enough: Run a "cold-start test." Open a brand new agent session using only repo contents, and see if it can answer five basic questions:

  1. What is this system? → AGENTS.md / README
  2. How is it organized? → ARCHITECTURE.md / module docs
  3. How do I run it? → Makefile / init.sh / package scripts
  4. How do I verify it? → Test, lint, and check commands
  5. Where are we now? → PROGRESS.md / feature list / git history

ACID principles for agent state management:

  • Atomicity: Each logical operation gets one git commit. If it fails midway, git stash to roll back. All or nothing — no "half done."
  • Consistency: Define "consistent state" verification predicates — all tests pass, lint reports zero errors. The agent runs verification after each operation.
  • Isolation: When multiple agents work concurrently, design state files to avoid race conditions. Each agent uses its own progress file, or use git branches for isolation.
  • Durability: Critical project knowledge lives in git-tracked files. Temporary state can stay in session memory, but cross-session knowledge must be persisted to files.
04

Why One Giant Instruction File Fails

You got serious about harness engineering and created an AGENTS.md. One month later it bloated to 300 lines, two months 450 lines, three months 600 lines. Then you notice the agent's performance is actually getting worse.

This is the "giant instruction file" trap. The most common vicious cycle: agent makes a mistake, you say "add a rule to prevent this," add it to AGENTS.md, it works temporarily, agent makes a different mistake, add another rule, repeat, file bloats out of control.

What goes wrong specifically:

  • Context budget gets eaten alive. A bloated instruction file might eat 10–20K tokens. A complex task might need to read dozens of source files, tool execution output also takes context, and conversation history accumulates.
  • Lost in the middle. Liu et al.'s 2023 research proved that LLMs use information in the middle of long texts significantly less effectively than at the beginning or end. A critical constraint buried at line 300 of a 600-line file has a very high probability of being effectively ignored.
  • Priority conflicts. The file mixes non-negotiable hard constraints ("never use eval()"), important design guidelines ("prefer functional style"), and specific historical lessons ("fixed a WebSocket memory leak last week"). These have completely different importance levels, but they look identical in the file.
  • Maintenance decay. Outdated instructions rarely get deleted. The result: the file only grows, never shrinks, and signal-to-noise ratio continuously declines.

The solution: progressive disclosure.

The entry file AGENTS.md stays at 50–200 lines, containing only the most frequently used items — project overview (one or two sentences), first-run commands, global hard constraints (no more than 15 non-negotiable rules), and links to topic documents.

Each topic document is 50–150 lines, organized by subject in the docs/ directory. The agent only reads them when needed. Like packing cubes in a suitcase — underwear in one cube, toiletries in another, chargers in a third. Finding things doesn't require emptying the whole bag.

Real-world result: A SaaS team's AGENTS.md ballooned to 600 lines. After refactoring to a routing file (80 lines) + topic documents, same task set success rate went from 45% to 72%. Security constraint compliance went from 60% to 95% — because it moved from the file middle to the routing file top.

05

Long-Running Tasks and Continuity

Context windows are finite. This isn't solvable by model upgrades — even if window sizes grow to 1M tokens, complex tasks will still exhaust them. Because agents aren't just generating code; they're understanding codebases, tracking their own decision history, processing tool output, and maintaining conversation context.

A deeper problem: information the agent produces isn't uniformly important. Intermediate reasoning steps contain the "why" of decisions. The final output only contains the "what" — the code itself. Compaction strategies usually preserve the latter but lose the former. The next session sees the code but doesn't know why it's written that way.

Anthropic discovered something fascinating: when agents sense context is running low, they exhibit "premature convergence" behavior — rushing to finish current work, skipping verification steps, or choosing a simple solution over the optimal one. They call this "context anxiety."

Core approach: Treat the agent like a brilliant engineer with amnesia. Before it "clocks out," it must write down critical information so the next "shift" agent can pick up quickly.

  • Progress file (PROGRESS.md): The most basic continuity artifact. Current state, completed items, in-progress items, known issues, next steps.
  • Decision log (DECISIONS.md): Record important design decisions and reasons. "What decision, why, when."
  • Git commits as checkpoints: Commit after completing each atomic unit of work. These are free, automatically versioned state snapshots.
  • init.sh or harness initialization flow: Specify "clock-in" and "clock-out" routines in AGENTS.md.

Real-world result: An agent was tasked with implementing a blog system with user authentication — 12 feature points, estimated 5 sessions. Without the journal: only 7 of 12 completed, 3 with hidden defects. With the journal: all 12 completed and verified. Rebuild time reduced ~78%, feature completion rate from 58% to 100%, hidden defect rate from 43% down to 8%.

06

Initialization as Its Own Phase

You start a new agent session and say "add a search feature." It jumps straight into coding — admirable enthusiasm. After 20 minutes it discovers the test framework isn't configured properly, spends another 10 fixing that, then the database migration script format is wrong. The search feature eventually gets added, but most time went to "figuring out how this project works" rather than writing the search feature.

Initialization and implementation have completely different optimization targets. Implementation optimizes for maximizing the quantity and quality of verified features. Initialization optimizes for maximizing the reliability and efficiency of all subsequent implementation.

When you mix them, the agent faces a multi-objective optimization problem — simultaneously building infrastructure and writing feature code. Without explicit priority setting, the agent naturally gravitates toward writing code (because that's directly visible output) while sacrificing infrastructure.

Treat initialization as a dedicated phase. The first session does only initialization — no business feature code at all. Initialization produces:

  1. Runnable environment. The project starts, dependencies are installed, no environment issues.
  2. Verifiable test framework. At least one example test passes. This proves the test framework itself is properly configured.
  3. Bootstrap contract document. A clear document telling subsequent sessions how to start, test, see progress, and pick up next steps.
  4. Task breakdown. Split the entire project into an ordered task list, each task with clear acceptance criteria.
  5. Git commit as checkpoint. After initialization completes, commit a clean checkpoint. All subsequent work starts from this checkpoint.

Anthropic's experimental data: projects using a dedicated initialization phase showed 31% higher feature completion rates in multi-session scenarios compared to mixed approaches. The key insight — time invested in the initialization phase is fully recovered in the next 3–4 sessions.

Warm start strategy: Don't start from an empty directory. Use a project template to preset standard directory structure, dependency configuration, and test framework. Bake common initialization steps into the template, leaving only project-specific initialization work.
