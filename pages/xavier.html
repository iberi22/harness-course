🧠 Xavier — Sistema de Memoria para Agentes

Cómo los patrones de harness engineering pueden mejorar Xavier, el sistema de memoria central del ecosistema SWAL.

¿Qué es Xavier?

Xavier es el sistema de memoria central para agentes AI del ecosistema SWAL. Está construido en Rust con SQLite-Vec y sigue una arquitectura hexagonal. Es el "cerebro" que permite a los agentes recordar entre sesiones y coordinar conocimiento.

Arquitectura actual:

  • Stack: Rust + SQLite-Vec + Tokio
  • API: HTTP (puerto 8003) con endpoints REST
  • Arquitectura: Hexagonal (puertos y adaptadores)
  • Memoria: Almacenamiento vectorial con búsqueda semántica
  • Endpoints clave: /health, /memory/search, /memory/add, /memory/stats
  • Estado: En migración de Xavier2 (Rust monolítico) a Xavier hexagonal

Problemas conocidos (del ARCHITECTURE_ANALYSIS.md):

  • 🔴 Duplicate session_event_handler — routes.rs tiene versión stateless, cli.rs tiene la funcional. La versión routes.rs no persiste nada.
  • 🔴 HTTP partido — Entre src/cli.rs y src/adapters/inbound/http/routes.rs
  • 🟡 OnceLock global — TimeMetricsPort usa module-level OnceLock en lugar de inyección de dependencias
  • 🟡 SimpleAgentRegistry sin trait — CliState.agent_registry tipado como Arc<SimpleAgentRegistry> en lugar de Arc<dyn AgentLifecyclePort>

Mejora: init.sh que verifique DB, migraciones, y conectividad. Clean-state checklist. Migration handoff entre versiones.

Patrones de Diseño Aplicados

🧠 Memory Persistence — El Patrón Fundamental

Xavier ya implementa la mayoría de este patrón naturalmente porque es un sistema de memoria. Pero puede mejorar con:

  • Two-step save invariant: Xavier ya separa escritura de contenido + indexación, pero el two-step explícito (primero guardar, luego indexar) previene orphaned topics si el proceso falla.
  • Jerarquía de 4 niveles: Organización > Usuario > Proyecto > Local. Xavier puede implementar routing de memoria por namespace con prioridades.
  • Bounded index + on-demand topics: Xavier ya tiene búsqueda semántica, pero un índice acotado con punteros a archivos temáticos reduciría latencia.

📐 Context Engineering — Retrieval Inteligente

Xavier puede implementar las 4 operaciones de context engineering para mejorar la calidad del retrieval:

  • Select: Solo recuperar memorias relevantes a la tarea actual del agente (filtro por namespace + semantic search)
  • Compress: Resumir memorias largas antes de devolverlas al agente. Xavier tiene el contexto completo, pero el agente tiene límite de tokens.
  • Isolate: Separar memorias por proyecto/agente para evitar contaminación cross-agent
  • Write: El patrón Save/Retrieve/Verify del OpenClaw AGENTS.md — después de guardar, verificar que se pueda recuperar

🔧 Tool Registry — API Safety

La API de Xavier expone operaciones de memoria a múltiples agentes. Tool registry pattern aplica a:

  • Fail-closed: Por defecto, un agente no puede leer memorias de otro agente
  • Permisos por namespace: Cada agente tiene permisos sobre su workspace_id
  • Rate limiting: Por agente, no global — evitar que un agente ruidoso degrade el servicio
  • Audit log: Todas las operaciones de memoria son registradas para trazabilidad

👥 Multi-Agent — Coordinación entre Agentes

Xavier es el centro de la coordinación multi-agente en SWAL. Patrones aplicables:

  • Coordinator: Xavier como orquestador que decide qué agente tiene acceso a qué memoria
  • Fork: Cada proyecto SWAL (SynapseTrader, Gestalt, etc.) tiene su namespace aislado
  • Swarm: Múltiples agentes pueden contribuir al mismo namespace compartido con coordinación
  • Context sharing: Xavier permite compartir contexto entre agentes de forma controlada (no todo a todos)

🔄 Lifecycle — Bootstrap y Mantenimiento

El lifecycle de Xavier puede mejorar con:

  • init.sh: Verificar SQLite-Vec, migraciones de esquema, health check de embedding pipeline
  • Clean-state checklist: Backup de índices, compactación de WAL, verificación de integridad
  • Hook system: Pre/post hooks para operaciones de memoria (ej: notificar a agentes cuando una memoria se actualiza)
  • Bootstrap dependency-ordered: Cargar namespaces, índices, y cachés en orden de dependencia

Roadmap de Mejora

Fase 1: Init y Verificación (inmediato)

init.sh para Xavier. Endpoint /health robusto. E2E test del ciclo save→search→retrieve. Clean-state checklist semanal.

Fase 2: Namespace Isolation (1-2 semanas)

Implementar fail-closed por defecto. Namespaces con permisos por agente/proyecto. Audit log de acceso a memoria.

Fase 3: Context Engineering (2-4 semanas)

Implementar Select/Compress/Isolate/Write en el retrieval. Budget management por agente. Resúmenes automáticos de memorias largas.

Fase 4: Arquitectura Hexagonal Completa (4-6 semanas)

Resolver los problemas de arquitectura del ARCHITECTURE_ANALYSIS.md. Unificar HTTP handlers. Eliminar OnceLock global. Traits para todos los puertos.

Fase 5: Multi-Agent Coordination (6-8 semanas)

Swarm coordination entre agentes. Sesiones compartidas con handoff. Hook system para eventos de memoria.
