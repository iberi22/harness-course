🤖 SynapseTrader — Aplicación de Harness Engineering

Cómo los patrones de diseño de harness se aplican a un bot de trading autónomo en Binance Futures con 55K LOC en Rust.

Estado Actual

SynapseTrader es un bot de trading en Rust (~55,850 LOC, 177 archivos .rs) con:

  • 8 agentes Hive — Marco de trabajo multi-agente para trading
  • 18 estrategias — EMARSI, GridTrading, DCA, LiquidSweep, MoneyFlow, etc.
  • Provider LLM — Integración con OpenCode Go para análisis de mercado
  • Daemon — Puerto 8989, loop continuo de trading
  • Dashboard — 7 páginas para monitoreo

Bugs recientes corregidos (2026-05-07/08):

  • 🔴 break→continue (L482,552 signal_aggregator.rs) — Symbol cap break bloqueaba 7 estrategias
  • 🔴 pluggable_context — Sin datos de volatility/volume en el context
  • 🔴 emit_signal threshold — Threshold 0.70 → 0.50 para detección realista
  • 🔴 GridTrading SL/TP — Stop Loss y Take Profit estaban invertidos
  • 🔴 PositionSizer — Margin mismatch entre paper ($28 usado vs $14 balance)
  • 🟡 StatusCacheUpdater — Posible panic, ahora con catch
  • 🟡 Dead code — ~350 líneas eliminadas

5-Subsystem Assessment

Evaluación del harness actual de SynapseTrader según el framework de 5 subsistemas:

📖 Instructions ⭐⭐⭐

Lo que hay: Skills synapse-trader y adaptive-strategy-control. AGENTS.md en el repo raíz.

Mejora: Progressive disclosure — un AGENTS.md corto que enlace a docs/ por estrategia. Instrucciones claras sobre qué leer antes de codificar.

📊 State ⭐⭐

Lo que hay: StatusCacheUpdater con signal aggregation. feature_list informal en memoria.

Mejora: feature_list.json con estado de cada estrategia (id, dependencias, status, evidencia). Progress log por estrategia.

✅ Verification ⭐⭐⭐

Lo que hay: Compilación Rust como gate. Tests unitarios por estrategia.

Mejora: init.sh que compile + corra tests antes de empezar. E2E tests de paper trading como verification gate.

🎯 Scope ⭐⭐

Lo que hay: Symbol caps y strategy isolation en el aggregator. Pero el bug break→continue muestra que los límites no eran correctos.

Mejora: One-feature-at-a-time policy. Definition of Done checklist para cada estrategia. Dependencias documentadas.

🔄 Lifecycle ⭐

Lo que hay: Daemon loop. No hay init.sh, no hay session handoff, no hay clean-state checklist.

Mejora: init.sh para bootstrap. Clean-state checklist. Session handoff template para el daemon.

Patrones de Diseño Aplicados

🧠 Memory Persistence — Aprendizajes de Estrategias

El bot necesita recordar entre ejecuciones qué estrategias funcionaron, en qué condiciones, y qué ajustes se hicieron. Actualmente esto se hace con variables en memoria que se pierden al reiniciar.

Implementación:

  • feature_list.json por estrategia: id, nombre, estado, evidencia de rendimiento
  • progress.md por sesión de trading: qué se probó, resultados, ajustes
  • Archivo de "lecciones aprendidas" por estrategia (evolucionable entre sesiones)
  • Two-step save: primero escribe el archivo de lección, luego actualiza el índice

📐 Context Engineering — Análisis de Mercado

El bot recibe datos de mercado (OrderBookAnalysis, VWAP, volatilidad) y necesita dar contexto al LLM provider para decisiones de trading.

Implementación:

  • Select: solo datos relevantes para la estrategia activa (no todo el orderbook)
  • Compress: resúmenes estadísticos en lugar de datos crudos
  • Isolate: contexto separado por par (no mezclar BTC y ETH)
  • Budget management: límite de tokens para el provider LLM

🔧 Tool Registry — Seguridad en Estrategias

Cada estrategia tiene acceso a herramientas de trading (órdenes, stop-loss, take-profit). Algunas son peligrosas si se usan incorrectamente.

Implementación:

  • Fail-closed: todo denegado hasta que la estrategia se registra explícitamente
  • Permisos por estrategia, no por herramienta
  • Pipeline de permisos: modo paper → modo real con confirmación
  • Log de todas las operaciones para auditoría

👥 Multi-Agent — Orquestación de Estrategias

SynapseTrader ya tiene 8 agentes Hive. El patrón de coordinación puede mejorar con los patrones de OpenClaw:

  • Coordinator: Un agente principal decide qué estrategia se activa según condiciones de mercado
  • Swarm: Múltiples estrategias evalúan el mismo par en paralelo, el aggregator decide
  • Fork: Cada par de trading corre su propio análisis independiente

🔄 Lifecycle — Ciclo de Vida del Daemon

El daemon necesita un lifecycle más robusto:

  • init.sh: Verificar conexión a Binance, cargar estado de estrategias, verificar balance
  • Clean-state: Antes de apagar, guardar estado, cerrar posiciones abiertas, loggear resumen
  • Handoff: Si el daemon se reinicia, debe retomar desde el último estado conocido

Roadmap de Mejora

Fase 1: Init y State (inmediato)

Crear init.sh + feature_list.json + progress.md. Establecer el ciclo de vida básico del daemon.

Fase 2: Verification Gates (1-2 semanas)

init.sh que corre tests y verifica compilación. E2E paper trading como verification gate antes de cada deploy.

Fase 3: Memory Persistence (2-3 semanas)

feature_list.json por estrategia con evidencia de rendimiento. Archivo de lecciones aprendidas. Handoff entre sesiones del daemon.

Fase 4: Scope Control (3-4 semanas)

Definition of Done por estrategia. Policy de una estrategia a la vez. Dependencias documentadas.

Fase 5: Multi-Agent Coordination (4-6 semanas)

Patrones Coordinator/Swarm/Fork para los 8 agentes Hive. Mejor aislamiento de contexto entre agentes.
